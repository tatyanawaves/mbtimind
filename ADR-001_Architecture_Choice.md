# ADR-001: Модульный монолит vs Микросервисы для MBTI-платформы

**Status:** Accepted  
**Date:** 2026-05-20  
**Deciders:** Tatyana (Founder / Product Owner), Technical Lead (TBD)

---

## Context

Мы строим B2B/B2G SaaS-платформу психологического тестирования на базе MBTI для трёх сегментов: корпоративный HR, университеты и школы Казахстана. Платформа подаётся на программу Astana Hub AI-Preneurs Almaty 2026.

**Ключевые ограничения:**

- **Команда:** 2-5 разработчиков на старте
- **Бюджет:** стартап-стадия, ограниченные ресурсы на инфраструктуру
- **Сроки:** MVP за 3 месяца, полноценный релиз за 12 месяцев
- **Нагрузка (MVP):** ~500 тестирований, 5-10 организаций
- **Нагрузка (12 мес.):** ~50 000 тестирований, 50-100 организаций
- **Data Residency:** данные граждан РК хранятся на территории Казахстана (Закон No. 94-V)
- **Стек:** FastAPI (Python), Next.js, Flutter, PostgreSQL, Redis, ClickHouse
- **Критичные модули:** Тестирование, Профиль, Рекомендации, Аналитика, Интеграции (1С, Moodle, Workday)

**Вопрос:** Какую архитектуру выбрать для старта — микросервисы или модульный монолит?

---

## Decision

**Принят модульный монолит (Modular Monolith)** с чёткими границами модулей и контрактами между ними, с плановой возможностью эволюции в микросервисы по мере роста нагрузки и команды.

---

## Options Considered

### Option A: Модульный монолит (Modular Monolith)

| Dimension | Assessment |
|-----------|------------|
| Сложность разработки | **Low** — единая кодовая база, единый процесс деплоя |
| Стоимость инфраструктуры | **Low** — 1-2 сервера, Docker Compose |
| Скорость выхода MVP | **High** — нет overhead на межсервисное взаимодействие |
| Масштабируемость | **Medium** — вертикальная + модульная декомпозиция |
| Подходит команде 2-5 чел. | **High** — минимальный DevOps overhead |
| Путь миграции | Модули выделяются в сервисы по достижении порогов |

**Pros:**
- Быстрый time-to-market: единый репозиторий, один процесс сборки и деплоя
- Низкая стоимость инфраструктуры: Docker Compose на 1-2 серверах в KZ дата-центре
- Простота отладки: все модули в одном процессе, нет сетевых вызовов между сервисами
- Транзакционная целостность: ACID-транзакции PostgreSQL без distributed transactions
- Рефакторинг дешевле: переименование, перемещение кода — обычные операции IDE
- Единая схема БД с Row Level Security для мультитенантности

**Cons:**
- Вертикальное масштабирование имеет потолок
- Все модули масштабируются вместе (нельзя отдельно масштабировать тестирование)
- При росте команды >10 чел. возрастает риск конфликтов в кодовой базе
- Требует дисциплины: без строгих границ модулей превращается в Big Ball of Mud

### Option B: Микросервисы (Microservices)

| Dimension | Assessment |
|-----------|------------|
| Сложность разработки | **High** — service discovery, API gateway, distributed tracing |
| Стоимость инфраструктуры | **High** — Kubernetes, service mesh, мониторинг каждого сервиса |
| Скорость выхода MVP | **Low** — значительный DevOps overhead с первого дня |
| Масштабируемость | **High** — независимое горизонтальное масштабирование |
| Подходит команде 2-5 чел. | **Low** — координация между сервисами при малой команде |
| Путь миграции | Изначально распределённая система |

**Pros:**
- Независимое масштабирование: тестирование можно масштабировать отдельно от аналитики
- Независимый деплой: обновление одного сервиса не затрагивает остальные
- Технологическая гибкость: разные сервисы могут использовать разные языки/БД
- Изоляция отказов: падение одного сервиса не роняет всю систему

**Cons:**
- Distributed complexity: eventual consistency, saga pattern, circuit breakers
- Стоимость инфраструктуры x3-5: Kubernetes кластер, Istio/Linkerd, Jaeger, ELK
- Сетевая латентность: каждый вызов между сервисами добавляет 1-10ms
- Команде 2-5 человек придётся тратить ~30-40% времени на инфраструктуру вместо бизнес-логики
- Distributed transactions для операций типа "создать результат + обновить профиль + сгенерировать рекомендации"

---

## Trade-off Analysis

### Скорость vs Масштабируемость
Модульный монолит даёт скорость сейчас за счёт масштабируемости позже. Для стартапа на стадии MVP и подачи в Astana Hub это правильный trade-off: главный риск — не построить продукт вовремя, а не не выдержать нагрузку.

### Простота vs Гибкость
Микросервисы дают гибкость развёртывания, но требуют зрелой DevOps-культуры. При команде 2-5 человек стоимость этой гибкости непропорционально высока.

### Точка перехода
Модульный монолит перестаёт быть оптимальным при:
- >10 000 одновременных тестирований (модуль тестирования выделяется первым)
- >10 разработчиков (конфликты в монорепе становятся bottleneck)
- >100 организаций с разными SLA (нужна изоляция нагрузки)

### Стратегия эволюции
1. **Месяцы 1-8:** Модульный монолит с чёткими bounded contexts
2. **Месяцы 9-12:** Выделение Test Engine в отдельный сервис (самый нагруженный модуль)
3. **Год 2+:** Выделение Recommendation Engine (ML-модель требует GPU)
4. **Год 3+:** Полноценный переход на микросервисы по мере роста

**Правила модулей:**
- Каждый модуль имеет свой Python package с public API (абстрактный интерфейс)
- Межмодульное общение только через Events (in-process event bus) или public API
- Прямой доступ к таблицам другого модуля запрещён — только через его API
- Shared Kernel содержит только базовые domain objects и утилиты

## Consequences

**Что становится проще:**
- Быстрый старт разработки — единый `docker-compose up` поднимает всё окружение
- Простая отладка — breakpoint в любом модуле, единый лог
- Дешёвый хостинг — один VPS в Казахстане на MVP
- Простые транзакции — ACID в PostgreSQL, никаких sagas

**Что становится сложнее:**
- Независимое масштабирование модулей (невозможно до выделения в сервис)
- При росте команды — merge conflicts в монорепе
- Необходима дисциплина в соблюдении границ модулей

**Что нужно будет пересмотреть:**
- При нагрузке >10K concurrent sessions — выделение Test Engine
- При подключении ML-модели рекомендаций (GPU) — выделение Recommendation Engine
- При росте команды >10 человек — оценка перехода на микросервисы

## Action Items

1. [ ] Определить структуру Python packages для каждого модуля
2. [ ] Реализовать in-process event bus (AsyncIO + dataclasses)
3. [ ] Настроить Row Level Security в PostgreSQL для мультитенантности
4. [ ] Создать шаблон модуля (cookiecutter) с тестами и документацией
5. [ ] Определить метрики для точки перехода к микросервисам (Prometheus alerts)
6. [ ] Документировать API-контракты между модулями (OpenAPI schemas)
